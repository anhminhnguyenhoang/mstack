### PR review

**You own one advisory verdict on someone's PR. Evidence first, then judgment, then a draft the human posts.** For "review PR 123", a PR URL, or `owner/repo#N`, in aiter, FlyDSL, or Triton. Every repo gets the same review: the `pr.review` port's rules and gates, the panel, and the repo's own conventions. A local diff with no PR is the **interrogate** skill alone. Your own PR runs the `pr.review` port after its draft opens (**Opening a PR**).

The review is advisory. mstack never picks the review event and never merges. Only the human picks `COMMENT`, `REQUEST_CHANGES`, or `APPROVE`.

1. **Resolve the PR and the forge.** Pin `owner/repo`, the number, the base ref, and the head SHA, per `../references/forge.md`.
2. **Fetch on the latest skills** with `scripts/pr-review.sh <owner/repo#N> [validation-report]`. It checks `gh auth status`, syncs the review skills to origin's latest, and runs the `pr.review` port's fetch step inside a per-commit snapshot of the PR's own repo, so every tree check reads that repo. A repo that does not ship the review skills gets them linked into its snapshot. It finds the repo's checkout in the Repos table of `~/.cursor/mstack/env.md`, else as the one checkout under `$HOME` whose `origin` is that repo. Exit 4: `gh` is older than 2.24 or not signed in. Tell the user which, ask them to install a current `gh` or to run `gh auth login` (a `GH_TOKEN` also works), and stop. Exit 7: no single checkout. Ask the user to clone it or to set it with `/setup-mstack env`, and stop. For a fork PR it does not run the PR's code, and says so. Pause per Autonomy: name the head repo and author, and rerun with `ALLOW_FORK_CODE=1` only after the human says yes. Record the snapshot paths it prints, and keep `$WORK`.
3. **Run the rest of the `pr.review` port** in full (`../references/ports.md`), from its Step 2 to its Step 7.6, in the snapshot it printed. Follow its gates and its own triage of whether the `pr.validate` port runs. Hold a GPU run to one locked GPU. A red gate means the step did not happen. Go back to it, never around it. On Triton, the `pr.validate` port reports `INCONCLUSIVE` (unsupported layout). For runtime evidence there, run the tests the PR adds through the `bench.run` port, and label the result advisory.
4. **Check the repo's conventions.** Hold the PR to its repo's row of **Per-repo conventions** in `opening-a-pr.md`: the title, the run-before-push gates, the tests it requires, and the body sections. A FlyDSL PR that changes the public API also runs the `api.check` port. Each miss is a finding that cites the row.
5. **Run the interrogate panel blind**, one reviewer per entry of the **interrogate** skill's Step 3, labeled `A`, `B`, and so on. For each, run `scripts/panel-gate.py prompt $WORK <label>`, send that file verbatim as the reviewer's read-only Task prompt, and pipe its reply verbatim into `scripts/panel-gate.py record $WORK <label>`. The script builds the prompt from `$WORK/pr.diff`, the PR's title and body, and the interrogate rubric, never the card. It records a reply only when it echoes that prompt's nonce. Never add the card, your notes, or a local `git diff` to the prompt. A docs-only or config-only PR skips the panel: write a one-line `skip:`, have another reader write `$WORK/independent.txt`, and pass `--no-panel <reason>` in step 8.
6. **Use a panel reviewer as the independent reader** of the `pr.review` port's Step 7.7. Run `scripts/panel-gate.py refute-prompt $WORK A`, which works only after reviewer `A`'s blind findings are recorded, so the card cannot anchor them. Resume reviewer `A` with that file verbatim, and pipe its reply into `scripts/panel-gate.py record-refute $WORK A`, which writes `$WORK/independent.txt` and checks one verdict per card finding. Then run the port's Step 8 gates.
7. **Merge into one verdict.** Start from the gated card. Add a panel finding only when it names a changed file and survives the card's refutation rule. Add the convention findings from step 4. Tag every finding with its sources, as in `[src: card, panel:A2]` or `[src: convention:FlyDSL]`. A finding both the card and the panel raised goes first. Each recorded panel finding that stays off the draft gets a line in `$WORK/panel/dispositions.txt`: `<id> DROPPED -- <the reason>`. Keep the card's Validation and Perf lines unchanged: the panel adds judgment, never evidence.
8. **Write the review draft** to `review-draft-<repo>-<N>.md`, in the ticket folder when there is one, else in the working directory. Top line: `Reviewed head: <40-hex sha>`. Then the merged card, at most five findings, each with problem, impact, an action verb, and its source tag. Then `## Inline`, with one `### <path>:<line>` or `### <path>:<start>-<end>` section per finding that has a line in the PR's new code, holding that finding's comment. Apply `/unslop`. Then run `scripts/panel-gate.py merge $WORK <draft>`. It stays red until every panel finding is on the draft or dropped with a reason, every finding has a source tag, the Validation and Perf lines match the card, and the `pr.review` skill's independent gate passes. Green, it stamps the draft. Any later edit, the human's included, needs the merge gate again. Show the draft in the reply.
9. **Stop at the draft.** Ask the human to approve it and to pick the event. Offer `COMMENT` as the default.
10. **Post only after approval** with `scripts/post-review.py <owner/repo> <N> <draft> <event>`, passing the event the human chose. It posts one review pinned to the draft's head SHA, with each `## Inline` section as a line comment. A section on lines outside the diff moves into the body, and it says how many. It refuses when the head moved (exit 3: re-run from step 2 or ask), when this user already reviewed that head (exit 5: `REPOST=1` only when the human asks), when the draft leaks a local path or an internal ticket key (exit 6: edit the draft), and when the draft's merge stamp is missing or stale (exit 8: run the merge gate of step 8 again). Without `gh`, run the merge gate, then use the forge's PR review row and make the same checks by hand first. Report the review URL.

**Reply:** the PR, head SHA, and skills snapshot reviewed. The merged verdict with its Validation and Perf lines. The draft path. The open decision: approve the draft and pick the event.
