### PR review

**You own one advisory verdict on someone's PR. Evidence first, then judgment, then a draft the human posts.** For "review PR 123", a PR URL, or `owner/repo#N`. A local diff with no PR is the **interrogate** skill alone. Your own PR runs the `pr.review` port after its draft opens (**Opening a PR**).

The review is advisory. mstack never picks the review event and never merges. Only the human picks `COMMENT`, `REQUEST_CHANGES`, or `APPROVE`.

1. **Resolve the PR and the forge.** Pin `owner/repo`, the number, the base ref, and the head SHA, per `../references/forge.md`.
2. **Fetch on the latest skills** with `scripts/pr-review.sh <owner/repo#N> [validation-report]`. It checks `gh auth status`, syncs the review skills to origin's latest in a per-commit snapshot, and runs the `pr.review` port's fetch step from the skill's own repo. Exit 4 means `gh` is not signed in: ask the user to run `gh auth login`, and stop. For a fork PR it does not run the PR's code, and says so. Pause per Autonomy: name the head repo and author, and rerun with `ALLOW_FORK_CODE=1` only after the human says yes. Record the snapshot SHA it prints, and keep `$WORK`.
3. **Run the rest of the `pr.review` port** in full (`../references/ports.md`), from its Step 2 to its Step 7.6. Read its scripts from the snapshot the wrapper ran in. Follow its gates and its own triage of whether the `pr.validate` port runs. Hold a GPU run to one locked GPU. A red gate means the step did not happen. Go back to it, never around it.
4. **Run the interrogate panel blind** on `$WORK/pr.diff`, with the PR body as the intent, never on a local `git diff`. Skip it for a docs-only or config-only PR with a one-line `skip:`, and use another reader in step 5.
5. **Use the panel as the independent reader** of the `pr.review` port's Step 7.7. Resume one panel reviewer, give it `$WORK/card.md` and `$WORK/merge_target.txt` with every finding false until defended, and write its verdicts to `$WORK/independent.txt`. Its blind review is already done, so the card cannot anchor it. Then run the port's Step 8 gates.
6. **Merge into one verdict.** Start from the gated card. Add a panel finding only when it names a changed file and survives the card's refutation rule. Note which source raised each finding. A finding both sources raised independently goes first. Keep the card's Validation and Perf lines unchanged: the panel adds judgment, never evidence.
7. **Write the review draft** to `review-draft-<repo>-<N>.md`, in the ticket folder when there is one, else in the working directory. Top line: `Reviewed head: <40-hex sha>`. Then the merged card, at most five findings, each with problem, impact, and an action verb. Apply `/unslop`. Show the draft in the reply.
8. **Stop at the draft.** Ask the human to approve it and to pick the event. Offer `COMMENT` as the default.
9. **Post only after approval** with `scripts/post-review.sh <owner/repo> <N> <draft> <event>`, passing the event the human chose. It pins the review to the draft's head SHA. It refuses when the head moved (exit 3: re-run from step 2 or ask), when this user already reviewed that head (exit 5: `REPOST=1` only when the human asks), and when the draft leaks a local path or an internal ticket key (exit 6: edit the draft). Without `gh`, use the forge's PR review row and make the same checks by hand first. Report the review URL.

**Reply:** the PR, head SHA, and skills snapshot SHA reviewed. The merged verdict with its Validation and Perf lines. The draft path. The open decision: approve the draft and pick the event.
