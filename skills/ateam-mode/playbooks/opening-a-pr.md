### Opening a PR

Invoked by Deliver (`playbooks/deliver.md`) when the output is code.

**Branch.** Name the branch `<prefix>/<topic>`, with `<prefix>` from the Git table of `~/.cursor/mstack/env.md` and `<topic>` a short kebab-case name for the change. Branch off the latest remote `main`, never a local `main`: `git -C <repo path> fetch <PR-target remote> main`, then `git -C <repo path> worktree add -b <prefix>/<topic> <worktree path> <PR-target remote>/main`. The PR-target remote is the one the Repos table names (for aiter and FlyDSL, the `ROCm/...` remote). When the prefix is `not set`, ask. Before new work, check whether that `main` already has the fix: a branch, a commit, or a change that supersedes it.

**Worktree.** For GPU work, make the worktree inside the container's mount, such as `<repo path>/.worktrees/<name>`, at the container path the Repos table of `~/.cursor/mstack/env.md` gives (`references/env.md`). The `<repo path>` is the path in the `repos` resource. Push to the push remote that table names, over the scheme it records (SSH or HTTPS), per `references/forge.md`. When it is `not set`, ask. A worktree outside a mount is invisible to the container. Builds and ISA checks may run in parallel across worktrees. Benchmarks queue on one locked GPU (the `bench.run` port). For other repos, work from a git worktree off main. Subagents inherit it. Multiple `Task` calls on the same branch each get their own worktree, or `git fetch && git reset --hard origin/<branch>` between them. For a dirty branch with unrelated work, save the changes as a patch, make a fresh worktree, and apply the patch. For a broken worktree, reset from main and redo only what is needed.

**Commits.** Commit liberally. Rebase into small, ordered commits before opening PRs. Each commit is a future PR. Make it landable and order it to tell the story. Amend when the fix belongs in a just-made commit. New commit when separable. Commit bodies don't restate the subject.

**Production-ready.** Before a PR, keep the diff minimal: the smallest change that holds the result (**principle-subtract-before-you-add**). Inline single-use helpers and merge duplicates. Remove every experimental, unused, or tuning knob, and keep only the active path as the default. A gated lever that won loses its gate and becomes the default. A lever that must differ by shape becomes a fixed shape dispatch in code, not a knob. Knobs are fine during development, to sweep the corners. Rerun the correctness gate and the perf numbers after the cleanup, and show they did not change.

**PRs.** Run the `style.gate` port, as the repo's row of **Per-repo conventions** names it, and the `comment-sicko` agent over the diff before commit and `/no-comments` before review. Write every PR title, description, and commit body with `/technical-writing` (every layer except Diátaxis, and apply the STE vocabulary rules: one word per action, keep articles, a plain verb over `-ing` where one works), then apply `/unslop`.

**Titles.** This is the default for a repo with no style of its own, such as this plugin. A repo in **Per-repo conventions** overrides the title, the body headings, and the gates. Conventional Commits `type(scope): subject`, no trailing period. Type such as `feat`, `fix`, `docs`, `refactor`, `test`, `chore`, or `perf`. Scope is the area, such as `mstack` or `ateam-mode`. Subject is short, imperative, and names a real symbol when one carries the change, for example `fix(mstack): retarget opening-a-pr babysit trigger`.

**Descriptions.** The PR body is a one-minute briefing, not a lab notebook, for a reviewer who has the diff. It says why the change exists, what it leaves out, what it could break, and how you proved it works. Write short, simple sentences with few identifiers, and no long blocks of text. The body becomes the squash commit body, so keep that commit under about 40 lines. Use `##` headings, not bold lead-ins, in this order, and drop a section with nothing to say:

- `## Why`: the problem and approach, 1 to 3 short sentences. No SHAs, rebase genealogy, or "based on main" preamble.
- `## What changed`: 1 to 3 short bullets. Name a real symbol or path only when it carries the change. Name both sides of a rename or retarget.
- `## Scope`: always. 1 to 3 short items on what it covers and what it deliberately leaves out (a follow-up, a known gap). No symbols, paths, or file-by-file essay.
- `## Tradeoffs`: only rejected alternatives a reviewer would otherwise ask about. Skip when there was no real choice.
- `## Blast Radius`: 1 to 2 sentences on who or what it touches and why that is safe or risky. If main is red, state the cost of leaving it red.
- `## Verification`: 1 to 3 bullets, each a real run path and its outcome. Perf: one primary number with its unit, `before → after`, and a link to the arena or swarm directory for the rest. No sample-size methodology, swarm recitals, or metric tables.

After the sections, attach videos or screenshots when they prove a claim. Full SHAs, swarm or arena lane recitals, lever-correction essays, file-by-file checklists, and "CLEAN" verdicts go in a linked artifact, not the body.

**Per-repo conventions.** Find the repo by name in the table and follow its row. Its path is in the `repos` resource. The row replaces the Titles and Descriptions defaults above. Ports in the rows resolve in `../references/ports.md`. Keep the briefing rules: why it exists, what it leaves out, what it could break, and one verified number. Neither aiter nor FlyDSL has a PR template file under `.github/`. Both use the ROCm PR template, without its Submission Checklist: `## Motivation` (the Why), `## Technical Details` (what changed, scope, tradeoffs, blast radius), `## Test Plan` (the commands, shapes, dtypes, arch, and baselines), and `## Test Result` (the correctness gate, then the numbers with units, before and after). Fold the extra sections of their `CONTRIBUTE.md` or `CONTRIBUTING.md` into those four. No internal ticket keys, ticket targets, rejected ideas, or test harness scripts in the body.

`ROCm/aiter`, `ROCm/FlyDSL`, `triton-lang/triton`, and `sgl-project/sglang` are public upstreams. Do not open a PR there unless the human says yes to your question first. Ask once the branch, title, and body are ready. Without a yes, prepare the branch, the title, and the body, then stop. After a yes, open it as a draft like every other PR. A draft on a public upstream is still public.

**Forge.** Resolve the forge before the first PR operation and keep that choice for create, edit, view, watch, and merge. Resolve it per `../references/forge.md`. Record the path and why.

**Built-in PR tool.** When the run provides a built-in PR tool, create (as a draft), edit, and retarget through it, never through a forge CLI. A CLI-made PR misses what the tool tracks. Use the resolved forge for everything the tool does not cover, and for every PR operation when the run has no such tool.

**Size and stacks.** Prefer five narrow PRs to one large PR. A stack is a base-branch chain. The root PR targets trunk. Each child branch rebases onto its parent's exact tip and its PR targets the parent branch. Without a built-in PR tool, per the resolved forge, create a child with `gh pr create --draft --base <parent-branch>`, and retarget one with `gh pr edit <pr> --base <parent-branch>`. Branch from trunk only for independent work. Rebase on trunk before substantial stack work.

**Readiness.** Every PR opens as a draft, and only as a draft. Never open one ready. Set `draft: true` on every creation call through a built-in PR tool. With `gh`, pass `--draft`. With MCP, set `draft: true`. If a PR still opens ready, convert it back to a draft, or stop and report when the path cannot (`gh pr ready --undo`, or the new-remote `update_pull_request` with `draft: true`). Marking a PR ready is the human's step. Never run `gh pr ready` or `draft: false`. Run `gh pr view <number>` before you refer to PR status.

**Babysit.** Opening a PR does not start a babysit. Post the URL and keep building. Finish the phase or stack first. Run a separate babysit pass only when the user asks for one after the whole stack exists. A babysit for each new PR stalls the build and spends checks on commits later waves restart. Push back when feedback drifts from intent.

A subagent that opens a PR runs `interrogate`, the `style.gate` port, the `comment-sicko` agent, and `/no-comments`, and posts the URL. It returns to the parent without babysitting, unless it is an Autopilot-full or Autopilot-stack owner. That owner's brief assigns the babysit loop and is the ask `playbooks/babysit.md` waits for. The owner starts the loop after its code-ready report, reports merge-ready or STACK-READY per its playbook, and is exempt from the rules here and in `playbooks/babysit.md` that hold babysitting until a whole stack is built.
